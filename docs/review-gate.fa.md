# راهنمای عملیاتی دروازهٔ تأیید بازبینی

[English](review-gate.md) · [فارسی](review-gate.fa.md)

ادغام به موفقیت CI، تأیید CodeRabbit روی آخرین کد PR، موفقیت بررسی ارائه‌دهندهٔ
SonarCloud و حل شدن گفتگوهای بازبینی نیاز دارد. بررسی **Review approval gate**
این شواهد را جمع‌بندی می‌کند؛ حفاظت بومی شاخه و بررسی‌های مستقل CI و Sonar نیز
جداگانه الزامی می‌مانند. [حفاظت شاخه](branch-protection.fa.md)،
[راه‌اندازی اولیه](bootstrap.fa.md) و [تنظیم Sonar](sonarqube.fa.md) را ببینید.

## وضعیت راه‌اندازی

در ۲۶ اکتبر ۲۰۲۶ حفاظت بومی هر سه مخزن فعال بود. ادغام PR مربوط به API به‌دلیل
نبود **Review approval gate** مسدود بود. App اختصاصی انتشار این بررسی هنوز
ساخته، نصب یا متصل نشده بود. وجود فایل‌های تنظیمات و موفقیت تست محلی به معنی
فعال بودن اتصال واقعی نیست. تا وقتی App واقعی بررسی الزامی را منتشر نکرده و
تمام شرایط دیگر برقرار نشده‌اند، ادغام باید مسدود بماند.

شاخهٔ اصلی خالی نمی‌تواند اولین پیاده‌سازی دروازهٔ خودش را معتبر اعلام کند.
ناشر باید از کدی که مستقلاً بررسی شده و بیرون از checkout مربوط به PR مستقر
شده اجرا شود. برای عبور از این مرحله حفاظت را موقتاً برندارید و کلید App را
در اختیار workflow متعلق به کد PR قرار ندهید.

## شواهد الزامی

[سیاست مورد اعتماد](../.github/review-policy.json) نام و شناسهٔ عددی مخزن،
شاخهٔ مقصد، شناسهٔ کاربر CodeRabbit و نام دقیق بررسی‌های CI و Sonar را مشخص
می‌کند. شناسهٔ مخزن `sepaseh/kernel-api` برابر `1431919186` است.

| شاهد       | نتیجهٔ الزامی                                                                                                                                  |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| PR         | باز و خارج از حالت پیش‌نویس، با مخزن و شاخهٔ مقصد مورد انتظار؛ SHA دقیق head و base در طول بررسی و انتشار تغییر نکند.                          |
| CodeRabbit | آخرین بازبینی `coderabbitai[bot]` با شناسهٔ کاربر `136622811` و نوع `Bot`، روی همان head فعلی، وضعیت `APPROVED` داشته باشد.                    |
| Sonar      | آخرین بررسی `SonarCloud Code Analysis` از App مربوط به SonarCloud با شناسهٔ `12526`، روی همان head، کامل و نتیجهٔ آن `success` باشد.           |
| CI         | تمام بررسی‌های ثبت‌شده در سیاست مورد اعتماد، از GitHub Actions با شناسهٔ App برابر `15368`، روی همان head کامل و دارای نتیجهٔ `success` باشند. |
| گفتگوها    | تمام رشته‌های گفتگوی بازبینی، حتی موارد قدیمی‌شده، حل شده باشند.                                                                               |

شواهد الزامیِ غایب، منتظر، ناموفق، لغوشده، ردشده از اجرا یا محدودشده به‌دلیل
سهمیه هرگز پذیرفته نمی‌شوند. موفقیت بررسی عمومی پیشرفت `CodeRabbit` کافی
نیست؛ تعداد تأییدها ممکن است با تأیید شخصی غیر از این ربات تکمیل شود. اجرای
scanner و قبولی دروازهٔ کیفیتِ ارائه‌دهندهٔ Sonar نیز دو شاهد جدا هستند.

## ساخت و نصب App ناشر

برای انتشار این بررسی از یک App اختصاصی، جدا از CodeRabbit و SonarCloud،
استفاده کنید. مراحل [ثبت App در GitHub](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app)
را دنبال کنید.

1. در حساب مالک `sepaseh`، صفحهٔ [New GitHub App](https://github.com/settings/apps/new)
   را باز کنید. نام پیشنهادی، در صورت آزاد بودن، `sepaseh-kernel-review-gate`
   است. نشانی حساب مالک یا پروژهٔ عمومی را به‌عنوان Homepage وارد کنید.
2. این ناشر از احراز هویت نصب App استفاده می‌کند؛ تنظیمات OAuth کاربر، callback
   و setup را استفاده نکنید. گزینهٔ **Active** در بخش webhook را بردارید؛
   اجرای تک‌مرحله‌ای یا پایشگر فعلی رویداد webhook دریافت نمی‌کند.
3. فقط این دسترسی‌های مخزن را تنظیم کنید: **Checks: Read and write**،
   **Contents: Read-only** و **Pull requests: Read-only**. دسترسی
   **Metadata: Read-only** به‌طور خودکار وجود دارد. دسترسی‌های نامرتبط را
   فعال نکنید؛ نوشتن Administration یا Workflows لازم نیست.
4. گزینهٔ **Only on this account** را انتخاب کنید، App را بسازید و App ID
   عددی آن را یادداشت کنید.
5. در **Install App**، نصب را روی حساب مالک انجام دهید و با **Only select
   repositories** فقط `kernel-api`، `kernel-admin` و `kernel-website` را
   انتخاب کنید. شناسهٔ نصب را از نشانی صفحهٔ تنظیمات نصب بردارید. هر اجرا
   توکن نصب را باز هم به همان یک مخزن مشخص‌شده در سیاست محدود می‌کند.
6. در **Credentials → Key pairs** یک کلید خصوصی بسازید و دریافت کنید. آن را
   در پوشه‌ای خصوصی و محافظت‌شده، بیرون از **تمام** مخزن‌ها و checkoutهای PR
   نگه دارید. محتوای کلید، JWT و توکن نصب نباید در گفتگو، کد، commit یا log
   قرار بگیرد. فقط App ID، شناسهٔ نصب و مسیر مطلق فایل کلید را در اختیار
   اپراتور مجاز قرار دهید.

برای تکمیل تنظیمات یا تعویض کلید، مستندات رسمی
[دسترسی‌ها](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app)،
[نصب](https://docs.github.com/en/apps/using-github-apps/installing-your-own-github-app)
و [نگهداری کلید خصوصی](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/managing-private-keys-for-github-apps)
را ببینید.

## اجرا از استقرار مورد اعتماد

نسخه‌های بررسی‌شدهٔ [ناشر](../scripts/publish-review-approval.mjs)،
[بررسی‌کنندهٔ شواهد](../scripts/check-review-approvals.mjs) در کنار آن و سیاست
را بیرون از checkout مربوط به PR مستقر کنید. اپراتور باید کد و سیاست مستقرشده
را بررسی کند؛ مطلق بودن مسیر به‌تنهایی فایل را قابل اعتماد نمی‌کند. سیاست،
اسکریپت یا تنظیمات اجرایی را از head مربوط به PR بارگذاری نکنید. کد PR نباید
به اعتبارنامهٔ نوشتن App دسترسی داشته باشد.

این متغیرها را فقط برای فرایند خارجی مورد اعتماد تنظیم کنید:

| متغیر                          | مقدار                                                            |
| ------------------------------ | ---------------------------------------------------------------- |
| `REVIEW_APP_ID`                | شناسهٔ عددی App اختصاصی ناشر.                                    |
| `REVIEW_APP_INSTALLATION_ID`   | شناسهٔ عددی نصب روی حساب مالک.                                   |
| `REVIEW_APP_PRIVATE_KEY_PATH`  | مسیر مطلق فایل کلید خصوصی، بیرون از همهٔ مخزن‌ها.                |
| `REVIEW_PUBLISHER_POLICY_PATH` | مسیر مطلق نسخهٔ مستقلاً بررسی‌شدهٔ `.github/review-policy.json`. |
| `REVIEW_PULL_NUMBER`           | شمارهٔ PR مورد نظر.                                              |
| `REVIEW_HEAD_SHA`              | SHA دقیق ۴۰ کاراکتری head فعلی PR.                               |
| `REVIEW_BASE_SHA`              | SHA دقیق ۴۰ کاراکتری base فعلی PR.                               |

Node را با مسیر **مطلق** ناشر مستقرشده اجرا کنید:

```sh
node /absolute/trusted/deployment/scripts/publish-review-approval.mjs
```

در ویندوز مسیر مطلق معادل را به کار ببرید. این مثال مسیر استقرار است و نباید
از داخل checkout مربوط به PR اجرا شود. ابزار اجرا در GitHub Actions یا
محیط رویداد آن را رد می‌کند. هویت App و نصب و محدودهٔ مخزن را بررسی می‌کند و
**Review approval gate** را روی head مشخص‌شده منتشر می‌کند. خروجی فقط
فرادادهٔ نتیجه، شامل `baseSha`، `checkRunId`، `headSha`، `passed` و `published`
است؛ خطا پیام پاک‌سازی‌شده و کد خروج غیرصفر دارد. برای عیب‌یابی، ثبت
اعتبارنامه‌ها را به ابزار اضافه نکنید.

در حفاظت بومی شاخه، بررسی الزامی **Review approval gate** را به شناسهٔ همین
App اختصاصی مقید کنید. بررسی همنام از App دیگر نباید پذیرفته شود. اعمال
حفاظت بر مدیران، باطل شدن تأییدهای قدیمی، حل شدن گفتگوها و بررسی‌های مستقل
CI و Sonar را نگه دارید. پیش از اعلام عملیاتی بودن اتصال، هویت App، commit
و نتیجهٔ بررسی واقعی را تأیید کنید.

## بررسی مجدد و رفع مانع

این ابزار فقط یک تصویر لحظه‌ای از شواهد منتشر می‌کند؛ سرویس دائمی نصب نمی‌کند
و خودکار به commit، بازبینی، تغییر گفتگو یا اجرای دوبارهٔ ارائه‌دهنده واکنش
نشان نمی‌دهد. پس از این تغییرات، اجرا را به اپراتور خارجی یا سرویس پایش/رویداد
مورد اعتماد بسپارید. push جدید، تأیید و شواهد head قبلی را نامعتبر می‌کند؛
تغییر base نیز بررسی تازه می‌خواهد. درست پیش از ادغام، head و base فعلی و
الزامات بومی را دوباره بررسی کنید.

اگر CodeRabbit بازبینی را اجرا نکرد، در چرخهٔ مجاز PR یک بار درخواست بازبینی
کنید. اگر سهمیه مانع شد، تا آزاد شدن سهمیه صبر کنید و head فعلی را دوباره
بازبینی کنید. تأیید قدیمی را استفاده نکنید، بازبینی اجرا‌نشده را موفق گزارش
نکنید و حفاظت را برای رفع مانع ضعیف نکنید. نبود دسترسی App، خطای ناشر یا پاسخ
ناقص ارائه‌دهنده، دروازهٔ الزامی را تأمین نمی‌کند.

GitHub تراکنش اتمیکی برای مجموع بازبینی‌ها، بررسی‌ها، گفتگوها و ادغام ارائه
نمی‌کند. بررسی مکرر head و base احتمال استفاده از شواهد قدیمی را کاهش می‌دهد؛
تضمین اتمیک یا تضمین هویت بازبین در برابر رفتار خصمانه ایجاد نمی‌کند. جداسازی
اعتبارنامه، استقرار مورد اعتماد، حفاظت بومی و بررسی نهایی اپراتور را حفظ کنید.
مخزن، PR، head و base، شناسهٔ check run، نتیجهٔ ارائه‌دهندگان و موانع باقی‌مانده
را ثبت کنید؛ اعتبارنامه‌ها را ثبت نکنید.
