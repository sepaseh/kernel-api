# آداپتورهای انتقال HTTP

[English](http-transport.md) · [فارسی](http-transport.fa.md)

آداپتورهای Hono مسیرها را به سرویس‌های موجود برنامه متصل می‌کنند. مرحلهٔ اجرای
محلی نقطهٔ اتصال و سرور Node را اضافه می‌کند؛ اجرای محلی به معنی آمادگی استقرار
یا ارسال عملیاتی کد یک‌بارمصرف نیست. فرانت‌اندها از طریق HTTP ارتباط می‌گیرند و
تغییر ناسازگار قرارداد باید هماهنگ منتشر شود.

آداپتورها ورودی را اعتبارسنجی، خطاهای معنایی را به پاسخ‌های محلی‌شده تبدیل،
مجوزها و مبدأ را کنترل و شناسهٔ درخواست را بدون اطلاعات ورود یا مسیر خام ثبت
می‌کنند. محدودکنندهٔ تلاش احراز هویت فقط در یک پردازه عمل می‌کند و محدودیت
توزیع‌شده ایجاد نمی‌کند؛ ورودی production به محدودسازی مستقل نیاز دارد.

این محدودکنندهٔ حافظه‌محدود پنجره‌های فعال را تا انقضا نگه می‌دارد. با پرشدن
ظرفیت ۱۰٬۰۰۰ پنجره، شناسه‌های تازه تا آزادشدن ظرفیت رد می‌شوند. بنابراین
اشباع عمدی همچنان می‌تواند موجب قطع دسترسی شود و محدودسازی مستقل در ورودی
یا یک سامانهٔ محدودسازی مشترک ضروری است.

ورود به ۲۰ تلاش برای هر هویت در پنجرهٔ ۱۵ دقیقه محدود است. ثبت‌نام، صدور
OTP، بازیابی رمز و تأیید کد ایمیل هرکدام در همان پنجره به ۱۰ تلاش برای هر
حوزه و هویت محدودند. درخواست و تأیید کد تغییر شماره به ۱۰ تلاش برای هر حوزه
و جفت عامل/حساب مقصد محدود است. هر PATCH دارای `mobile` یک تلاش مصرف می‌کند،
حتی اگر شماره تغییر نکرده باشد. این محدودیت‌ها درون‌فرایندی‌اند، نه توزیع‌شده
یا مبتنی بر IP.

محدودکنندهٔ تلاش، `429` را با `Retry-After` بر حسب ثانیه برمی‌گرداند.
صدور OTP همچنین فاصلهٔ مستقل ۱۲۰ ثانیه‌ای دارد؛ پاسخ `429` آن می‌تواند پیام
دیگری داشته باشد و الزاماً `Retry-After` ندارد. درخواست کد تأیید ایمیل از
فاصلهٔ صدور OTP استفاده می‌کند؛ محدودکنندهٔ تلاش به تأیید کد ایمیل اعمال می‌شود.

## تغییر شمارهٔ موبایل

تغییر شماره به اثبات کنترل **شمارهٔ جدید** پیش از ثبت نیاز دارد:

| مسیر           | درخواست کد                                        | تأیید تغییر                     |
| -------------- | ------------------------------------------------- | ------------------------------- |
| پروفایل خود    | `POST /account/request-mobile-verification`       | `PATCH /account/update-profile` |
| مدیریت کاربران | `POST /users/:userId/request-mobile-verification` | `PATCH /users/:userId`          |

بدنهٔ JSON هر دو درخواست کد `{ "mobile": "..." }` است و پاسخ شامل
`{ "expires_in": ..., "remaining_seconds": ... }` می‌شود. برای تأیید،
بدنهٔ `{ "mobile": "...", "otp": "..." }` را به PATCH مربوط بفرستید؛
تغییر اختیاری `first_name` و `last_name` نیز می‌تواند همراه آن باشد. وقتی شماره
واقعاً تغییر می‌کند، کد الزامی است. نشست احراز‌شده باید در هر دو مرحله فعال بماند.

مسیر پروفایل فقط برای حساب واردشده است. مسیر مدیریت به مجوز `users.update`
نیاز دارد؛ تغییر شمارهٔ حساب دیگری علاوه بر آن فقط برای مدیر سیستم فعال مجاز
است. مدیر سیستم هنگام تغییر حساب دیگری می‌تواند با کنترل شمارهٔ جدید تغییر را
بدون رضایت مالک فعلی حساب انجام دهد: کد، شمارهٔ قبلی یا موافقت مالک قبلی را
تأیید نمی‌کند. بهره‌برداران و مصرف‌کنندگان باید این ریسک پذیرفته‌شده را لحاظ کنند.

کد به مسیر، عامل، نشست، حساب مقصد، شمارهٔ قبلی و شمارهٔ جدید وابسته است. هنگام
تأیید، نشست و مجوز دوباره بررسی می‌شوند و مصرف کد و تغییر شماره در یک تراکنش
انجام می‌گیرند. کد منقضی، نادرست، مصرف‌شده یا نامنطبق رد می‌شود؛ شکست تغییر
به مصرف جزئی کد منجر نمی‌شود. هویت داخلی احراز هویت موجود حفظ می‌شود.

ارسال عملیاتی OTP در این مرحله وجود ندارد. مصرف‌کنندگان نباید تحویل کد در
production یا قابل‌اجرا بودن API را از انتشار این آداپتورها فرض کنند. این تغییر
با رفتار قبلی به‌روزرسانی شماره سازگار نیست؛ انتشار و بازگشت نسخهٔ API و
مصرف‌کنندگان مستقل را هماهنگ کنید تا کلاینت‌ها پیش از تغییر شماره کد بگیرند و
`otp` را ارسال کنند.

پیش از خواندن بدنهٔ multipart، درخواست بارگذاری احراز هویت می‌شود. لایهٔ انتقال
به‌جای اتکا به `Content-Length` بایت‌های واقعی جریان را می‌شمارد و کل بدنه را
به سقف فایل تنظیم‌شده به‌علاوهٔ ۶۴ کیلوبایت برای قالب و فیلدها محدود می‌کند.
برنامه نیز بایت‌های خود فایل را جداگانه اعتبارسنجی می‌کند. آزمون‌ها از پورت‌های
مصنوعی و آداپتور محلی Node با fixture موقت استفاده می‌کنند و رفتار storage مستقر
را اثبات نمی‌کنند. انتشار و بازگشت نسخه باید با مصرف‌کنندگان مستقل HTTP هماهنگ
شود؛ تست سرور محلی به معنی آمادگی production نیست.
