# راه‌اندازی قواعد کار مخزن

[English](bootstrap.md) · [فارسی](bootstrap.fa.md)

پروژهٔ منتشرشده در مرحلهٔ **قواعد و گردش کار** است. فهرست دقیق فایل‌های آن در
[bootstrap-policy.json](../.github/bootstrap-policy.json) قرار دارد. این مرحله
بازبینی خودکار را آماده می‌کند؛ اجرای API، migrationهای پایگاه داده و کالکشن HTTP
با این بررسی‌ها منتشر یا تأیید نمی‌شوند. وضعیت آمادگی برنامه همچنان false است.

از نسخهٔ Node.js در [.nvmrc](../.nvmrc) استفاده کنید؛ نصب npm و فایل محیط لازم نیست:

```sh
node scripts/validate-bootstrap.mjs
node --test scripts/check-pr-size.test.mjs scripts/validate-bootstrap.test.mjs
```

پیش از تولید پوشش، یک checkout جدا یا خروجی محتوای دقیق کامیت پیشنهادی را بررسی
کنید. فایل اضافی یا مفقود، لینک نمادین، مسیر خصوصی و خطای نحوی JSON یا JavaScript
رد می‌شود. فایل‌های کامیت‌نشدهٔ خارج از این مجموعه نباید PR ناقص را موفق نشان دهند.

[گردش کار راه‌اندازی](../.github/workflows/bootstrap.yml) با گزارشگر داخلی Node،
فایل واقعی `coverage/lcov.info` را تولید می‌کند. این پوشش اسکریپت‌های گردش کار است
و پوشش برنامهٔ API نیست. گزارش‌های تولیدشده وارد کامیت نمی‌شوند.

## چرخهٔ Pull Request

1. روی شاخهٔ مشخص `codex/<purpose>` کار و کل تفاوت با مبنا را بررسی کنید.
2. تعداد فایل‌های تغییرکردهٔ GitHub حداکثر **۱۰۰** باشد. افزودن، حذف، تغییر نام و
   فایل باینری همگی حساب می‌شوند؛ تغییر نام در فهرست GitHub یک مورد است.
3. محتوای دقیق پیشنهادی و بررسی‌های مرحلهٔ اعلام‌شده را اجرا کنید.
4. شاخه و PR را با [قالب](../.github/PULL_REQUEST_TEMPLATE.md)، شواهد واقعی تست و
   محدودیت‌ها ارسال کنید. کار ناقص به صورت Draft باقی بماند.
5. یافته‌های CodeRabbit را بخوانید، عیب‌های واقعی را اصلاح و بررسی‌های مرتبط را
   تکرار کنید. بازبینی انجام‌نشدهٔ ربات، بازبینی کامل کد نیست.
   اگر بازبینی خودکار انجام نشد، یک‌بار `@coderabbitai review` را در کامنت PR
   بنویسید. مخزن‌های عمومی با ستارهٔ کمتر از حد سرویس در حال حاضر به این درخواست
   دستی نیاز دارند؛ وضعیت موفقِ بازبینی انجام‌نشده شاهد بررسی کد نیست.
6. در صورت تنظیم سرویس، تحلیل واقعی Sonar و نتیجهٔ دروازهٔ کیفیت را بررسی کنید.
   نبود تنظیمات، تحلیل در دسترس‌نبودن و شکست تحلیل وضعیت‌های جدا هستند.
7. ادغام پس از بررسی‌های الزامی و بازبینی مالک انجام شود. این مرحله ادغام خودکار،
   استقرار و ساخت تگ انتشار را فعال نمی‌کند.

[سیاست PR](../.github/workflows/pr-policy.yml) کد شاخهٔ پیش‌فرض مورد اعتماد را با
دسترسی فقط‌خواندنی و روی کامیت ثابت `github.workflow_sha` اجرا می‌کند. در این رخداد
دارای دسترسی، کد سر PR یا شاخهٔ مقصد بازبینی‌نشده checkout نشود. صفحه‌بندی کامل و ثابت‌ماندن سر و مبنای PR الزامی
است؛ پاسخ ناقص API باعث شکست می‌شود. PR اول بررسی اندازهٔ بدون دسترسی نوشتن از
شاخهٔ خودش هم دارد، چون مبنای خالی هنوز سیاست را ندارد.

حفاظت اولیهٔ `main` وجود PR، موفقیت بررسی **Bootstrap governance (API not
published)** از GitHub Actions و حل گفتگوها را لازم می‌داند. این حفاظت برای مدیران
هم برقرار است؛ force push و حذف شاخه را منع و تاریخچهٔ خطی را الزامی می‌کند. تأیید
نفر دوم الزامی نیست. ارزیابی دروازهٔ کیفیت Sonar مشورتی می‌ماند. پس از ادغام اولیه،
اجرای واقعی **PR file limit** از گردش کار مورد اعتماد را بررسی و سپس آن بررسی را
الزامی کنید. هنگام ورود مرحلهٔ قابل اجرا، بررسی‌های منسوخ راه‌اندازی را با تست‌های
تأییدشدهٔ برنامه جایگزین کنید تا حفاظت شاخه به یک بررسی حذف‌شده وابسته نماند.

سیاست رخدادهای Actions این مخزن، `pull_request_target` را فقط برای
`.github/workflows/pr-policy.yml` مجاز می‌کند. این استثنا محدود بماند و checkout
ثابت مورد اعتماد حفظ شود؛ محدودیت عمومی این رخداد در مخزن‌های عمومی، مجوز اجرای
کد PR با دسترسی بالاتر نیست.

ورود کد اجرایی نیازمند تغییر مرحلهٔ بازبینی‌شده، وابستگی‌های منسجم و بررسی محتوای
واقعی کامیت است. فهرست مجاز این مرحله نباید گسترش یابد و ادعا شود که رفتار برنامه
تأیید شده است. هنگام ورود API قابل اجرا، اعتبارسنجی کامل و تست‌های مصنوعی پایگاه
داده، احراز هویت و ذخیره‌سازی فعال شوند. سقف ۱۰۰ فایل حفظ و PRهای پیش‌نیاز مشخص
شوند. این بررسی‌ها جایگزین تست‌های الزامی برنامه نیستند و رفتار نمایشی را توجیه
نمی‌کنند.
