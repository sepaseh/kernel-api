# مرحلهٔ سرویس‌های کاربردی و اعتبارسنجی

[English](bootstrap.md) · [فارسی](bootstrap.fa.md)

این مجموعه در مرحلهٔ **سرویس‌های کاربردی (`application-services`)** است.
فهرست دقیق آن در [bootstrap-policy.json](../.github/bootstrap-policy.json)
قرار دارد و مقدار `applicationReady` همچنان **false** است. قراردادهای خالص،
اجزای پایه، رابط‌های آداپتر و هفت سرویس حساب، احراز هویت، تقویم، فایل، نقش،
تنظیمات و کاربر منتشر شده‌اند. HTTP، پایگاه داده و migration، آداپترهای واقعی
احراز هویت و ذخیره‌سازی و استقرار در این مرحله وجود ندارند.

برای نقشهٔ سورس [README](../README.fa.md)، برای مالکیت و محدودیت‌ها
[معماری](architecture.fa.md) و برای روش تغییرات
[راهنمای مشارکت](../CONTRIBUTING.fa.md) را بخوانید. پروژه ابزار توسعهٔ محلی
دارد و وابستگی زمان اجرا ندارد؛ API راه‌اندازی نمی‌کند.

## مجموعهٔ دقیق فایل‌ها و بررسی کامل مرحله

از Node.js در [`.nvmrc`](../.nvmrc)، محدودهٔ پشتیبانی‌شده در
[`package.json`](../package.json) و npm همراه همان نسخهٔ Node، مطابق CI،
استفاده کنید:

```sh
npm ci
npm run validate -- full
```

[فهرست مرجع اعتبارسنجی](../.agents/validation.json) تمام بررسی‌های الزامی
این مرحله را مشخص می‌کند: یکپارچگی مجموعهٔ فایل‌ها، سیاست معنایی CI، audit
وابستگی‌ها، مرزهای سورس، نوع‌ها، lint، قالب‌بندی، تست همراه با پوشش و تست ابزار audit.
پیش از commit یا تحویل PR که صریحاً مجاز شده است، تمام پروفایل `full` را
اجرا کنید. تست محدود حین توسعه جای آن را نمی‌گیرد.

هر PR، شامل پیش‌نویس و تغییر صرفاً مستندات، پس از `npm ci` تمام نُه بررسی
الزامی را با `npm run validate -- full` اجرا می‌کند. فیلتر مسیر تغییرکرده یا
شاخهٔ PR این بررسی را محدود نمی‌کند. اجراکننده پیش از شروع، کامل بودن فهرست
را بررسی می‌کند: هر بررسی الزامی دقیقاً یک بار در `full` حاضر است؛ شناسهٔ تکراری،
بررسی ناشناخته یا اختیاری پذیرفته نمی‌شود. ترتیب اعلام‌شده و توقف روی اولین
شکست حفظ می‌شوند.

سیاست معنایی YAML محتوای واقعی workflow را می‌سنجد و به قالب نوشتاری آن متکی
نیست. کلید تکراری، محدود شدن triggerهای PR، اجرای کامل شرطی یا قابل چشم‌پوشی،
ترتیب نادرست نصب و بررسی کامل، shell یا پوشهٔ اجرای سفارشی و تغییر اعلام‌نشدهٔ
runner یا job رد می‌شوند. تمام بررسی‌های مرحلهٔ فعلی به job با نام `check`
روی Ubuntu تعلق دارند؛ مرحلهٔ چند-job بعدی باید آگاهانه این سیاست را به‌روز کند
تا بررسی مختص یک سیستم‌عامل، بی‌صدا روی runner دیگر اجرا نشود.

checkout یا خروجی جداگانهٔ محتوای دقیق پیشنهادی را بررسی کنید. محافظ فهرست،
فایل نگهداری‌شدهٔ مفقود یا اضافی، لینک نمادین و مسیر خصوصی را رد می‌کند؛
سورس کامیت‌نشدهٔ اضافه نباید PR ناقص را کامل نشان دهد. این مرحله به هر هفت
ماژول سرویس و پنج فایل تست کاربردی اعلام‌شده نیاز دارد؛ صرف افزودن یک مسیر به
فهرست مجاز، سورس بررسی‌نشده، آداپتر یا نقطهٔ ورود قابل اجرا را مجاز نمی‌کند.
**سقف ۱۰۰ فایل برای فهرست فایل‌های تغییرکردهٔ هر PR در GitHub است** و تعداد کل
فایل‌های مخزن را محدود نمی‌کند.

تست‌ها به محیط واقعی، پایگاه داده، bucket یا API در حال اجرا نیاز ندارند.
اسرار و دادهٔ زمان اجرا را وارد سورس یا fixtureهای تست نکنید.

## محدودهٔ شواهد

تست‌های کاربرد با رابط‌های ساختگی، اعتبارسنجی، مجوزها، خطاهای معنایی، مرجع
زبان، ترتیب عملیات و حفظ خطای اصلی هنگام پاک‌سازی جبرانی فایل را بررسی می‌کنند.
تست‌های پایه و ابزارهای مخزن نیز در بررسی کامل حفظ می‌شوند.

دستور `npm run test:coverage` از سورس کاربردی منتشرشده و اسکریپت‌های تست‌شدهٔ
همین checkout فایل واقعی `coverage/lcov.info` تولید می‌کند. تست جداگانهٔ ابزار
audit هم در پروفایل کامل الزامی است. گزارش تولیدشده commit نمی‌شود.
رابط ساختگی شاهد تراکنش واقعی DB، رقابت هم‌زمان، cookie، ارسال OTP یا ذخیره‌سازی
واقعی نیست و آمادگی API قابل اجرا را ثابت نمی‌کند.

از [CI موجود](../.github/workflows/ci.yml) و
[گردش‌کار Sonar](../.github/workflows/sonar.yml) استفاده کنید؛ گردش‌کار scanner
تکراری نسازید. پیش از گزارش موفقیت، اجرای واقعی میزبانی‌شده، revision تحلیل و
دروازهٔ کیفیت ارائه‌دهنده را بررسی کنید. [تنظیم Sonar](sonarqube.fa.md) را ببینید.

## چرخهٔ Pull Request

1. روی شاخهٔ مشخص `codex/<purpose>` کار و کل تفاوت با مبنا را بررسی کنید.
2. هر PR حداکثر **۱۰۰ مورد فایل تغییرکرده در GitHub** داشته باشد. افزودن،
   حذف، تغییر نام و فایل باینری حساب می‌شوند؛ تغییر نام در GitHub یک مورد است.
3. تمام بررسی‌های مرحلهٔ فعلی را روی مجموعهٔ دقیق پیشنهادی اجرا و revision،
   مرحله، دستورها، نتیجه‌ها و محدودیت‌ها را ثبت کنید.
4. با اجازهٔ صریح، PR را با [قالب](../.github/PULL_REQUEST_TEMPLATE.md)
   منتشر کنید. کار ناقص در حالت Draft بماند.
5. [پیش‌شرط CodeRabbit](sonarqube.fa.md#پیش-از-درخواست-coderabbit) را کامل کنید:
   تمام بررسی‌های الزامی به‌جز خود CodeRabbit، اجرای scanner و دروازهٔ کیفیت واقعی
   باید برای head دقیق و فعلی موفق باشند. گزارش کامل و مرتبط Sonar باید در همهٔ
   شدت‌ها، شامل موارد قبلی، صفر issue باز یا حل‌نشده داشته باشد. شاهد مفقود،
   در انتظار، اجرا‌نشده، ناموفق یا قدیمی درخواست را مسدود می‌کند؛ هر commit جدید
   این پیش‌شرط را نامعتبر می‌کند.
6. فقط پس از آن در چرخهٔ مجاز یک درخواست بفرستید. یافته‌ها را بخوانید، عیب‌ها را
   اصلاح و پیش از بازبینی مجدد مرحلهٔ ۵ را تکرار کنید. سهمیه و حداکثر یک درخواست
   در حال انجام برای هر head را رعایت کنید. پیش از درخواست تازه، گذشته بودن حداقل
   یک ساعت از آخرین بازبینی CodeRabbit همین مخزن را بررسی کنید. وضعیت اجرا‌نشده یا مثبت کاذب مستندشده
   ولی همچنان باز، پیش‌شرط را برآورده نمی‌کند؛ با trigger خودکار، suppression یا
   ضعیف کردن الزامات آن را دور نزنید.
7. ادغام فقط پس از موفقیت CI الزامی، بررسی‌های بومی CodeRabbit و Sonar،
   بازبینی تأییدشده و حل گفتگوها انجام شود.
   [حفاظت شاخه](branch-protection.fa.md) را رعایت کنید؛ وجود تنظیمات یا وضعیت
   پیشرفتِ بازبینی اجرا‌نشده شاهد بازبینی واقعی نیست.

[سیاست PR](../.github/workflows/pr-policy.yml) کد شاخهٔ پیش‌فرض مورد اعتماد
را با دسترسی فقط‌خواندنی و روی کامیت ثابت `github.workflow_sha` اجرا می‌کند.
در این رویداد دارای دسترسی، کد head مربوط به PR یا checkout مقصد بررسی‌نشده
را اجرا نکنید. صفحه‌بندی کامل و ثابت بودن head و base مربوط به PR برای شاهد
تعداد فایل‌ها الزامی است.

## ورود به مرحلهٔ قابل اجرا

انتقال HTTP و آداپترهای واقعی را با تغییرات منسجم و
بازبینی‌شده اضافه کنید. هنگام ورود این پیاده‌سازی‌ها تمام تست‌های HTTP،
پایگاه داده، احراز هویت و ذخیره‌سازی را فعال و پروفایل کامل مرجع را گسترش
دهید. فهرست فایل‌ها، گردش‌کارها، محدودهٔ تحلیل و نام بررسی‌های حفاظت شاخه را
هماهنگ به‌روز کنید؛ پیش از کنار گذاشتن بررسی قدیمی، اجرای بررسی جایگزین را
تأیید کنید.

موفقیت بررسی‌های سرویس کاربرد مجوز true کردن آمادگی برنامه نیست. گسترش بی‌ضابطهٔ
فهرست مجاز، رفتار نمایشی یا سورس کامیت‌نشدهٔ نامرتبط را شاهد کارکرد API قابل
اجرا ندانید. سقف ۱۰۰ فایل برای هر PR در مراحل بعد نیز حفظ شود.
