# برنامه‌ریزی تغییر API

[English](change-workflow.md) · [فارسی](change-workflow.fa.md)

رفتار درخواستی، مخزن مسئول، مصرف‌کنندگان و سناریوهای پذیرش قابل مشاهده را ثبت
کنید. با [مسیر‌یابی](source-navigation.fa.md)، قرارداد، سرویس، آداپتور و
آزمون‌های مرتبط را بخوانید. تغییرات محلی موجود را حفظ و اعتبارنامه و دادهٔ
خصوصی را از داده‌های آزمون کنار بگذارید.

ورودی نامعتبر، مجوز، سازگاری داده و قرارداد را در صورت ارتباط توضیح دهید.
پیش از پیاده‌سازی وابستگی مهاجرت یا انتشار را مشخص، سپس بررسی‌های متمرکز و
[اعتبارسنجی کامل](validation.fa.md) را پیش از تحویل مجاز اجرا کنید. اجرای
انجام‌نشده یا تأیید راه دور دریافت‌نشده را گزارش نکنید.

## رکورد تغییر

برای اتصال درخواست به پیاده‌سازی و بررسی، این رکورد را تکمیل کنید و همراه کار
محلی یا issue و PR مجاز نگه دارید. نمونه و بررسی اجرا‌نشده شاهد تکمیل نیستند.

```text
درخواست، منبع و تاریخ:
رفتار الزامی و موارد صریحاً خارج از محدوده:
مخزن مالک و مصرف‌کنندگان متأثر:
خط مبنا و محدودهٔ سورس، شامل تغییرات محلی موجود:
سناریوی پذیرش: محرک، نتیجهٔ قابل مشاهده و روش بررسی:
ورودی نامعتبر، قدیمی یا بدون مجوز و نتیجهٔ مورد انتظار:
وابستگی‌ها و تصمیم‌های عملیاتی:
گام‌های پیاده‌سازی و فایل‌های مالک:
سازگاری داده، مهاجرت و HTTP؛ انتشار و بازگشت:
داده‌های مصنوعی و پاک‌سازی آن‌ها:
شناسهٔ بررسی یا نمایهٔ مرتبط در .agents/validation.json:
نتایج مشاهده‌شده، شکست‌ها و بررسی‌های اجرا‌نشده:
کار باقی‌مانده و مالک:
```

در صورت ارتباط، سناریوهای تراکنش، نشست، حریم خصوصی یا بازیابی را نیز ثبت کنید.
رفتار بک‌اند در API مالک باقی بماند و تغییر ناسازگار HTTP با مصرف‌کنندگان
هماهنگ شود. به‌جای ساخت فهرست مستقل بررسی‌ها، از مرجع اعتبارسنجی استفاده کنید
و مستندات انگلیسی و فارسی را با هم به‌روز نگه دارید.

در تغییر حذف، وضعیت یا رابطه‌ها، [قاعدهٔ چرخهٔ داده](../.agents/rules/data-lifecycle.md) را بخوانید و ثبت کنید تراکنش مسئول چگونه از رکوردهای وابسته محافظت می‌کند. برای صفحهٔ متکی به API، از [تحویل قرارداد صفحهٔ کلاینت](collection-guide.fa.md) استفاده کنید تا رفتار موجود از تغییر پیشنهادی قرارداد جدا باشد.
