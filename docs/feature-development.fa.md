# تغییر رفتار API

[English](feature-development.md) · [فارسی](feature-development.fa.md)

پیش از ویرایش، قرارداد HTTP، سیاست کاربردی، port و آداپتور مسئول را مشخص کنید.
سیاست کاربردی را مستقل از زیرساخت نگه دارید؛ درخواست و پاسخ را در مرز HTTP
تبدیل و قواعد پایگاه داده را به‌صورت اتمیک در آداپتور اجرا کنید. تغییر ناسازگار
قرارداد را با مصرف‌کنندگان مستقل هماهنگ کنید.

در تغییر حذف یا رابطه‌ها، ارجاعات کاری را حفظ کنید و به‌جای حذف نرم یا حذف
بی‌صدای وابستگی‌ها، تعارض معنایی موجود را برگردانید. [محدودیت‌های پایگاه داده](database-schema.fa.md)
و [انتقال HTTP](http-transport.fa.md) را ببینید.

برای رفتار و خطاهای مرتبط آزمون متمرکز با دادهٔ موقت بنویسید. مستندات انسانی
انگلیسی و فارسی را با هم به‌روز و پیش از تحویل مجاز، [اعتبارسنجی](validation.fa.md)
الزامی را اجرا کنید.

برای صفحه‌ای که از API استفاده می‌کند، [تحویل قرارداد صفحهٔ کلاینت](collection-guide.fa.md) را بر اساس مسیرها، مجوزها و نمونه‌های پاسخ موجود تکمیل کنید. نیاز پیشنهادی به تغییر قرارداد را جداگانه ثبت و تغییر ناسازگار HTTP را با برنامهٔ مصرف‌کننده هماهنگ کنید.

برای تغییر حذف، status یا رابطه، [قاعدهٔ مرجع چرخهٔ داده](../.agents/rules/data-lifecycle.md)
و schema، تراکنش و نمونهٔ HTTP مالک را بخوانید. حذف نرم ممنوع است و رکوردی که
رکورد کاری یا انتساب دیگری از آن استفاده می‌کند نباید حذف شود. در این حالت خطای ۴۰۹ با پیام
ترجمه‌شده بدهید که ابتدا باید تکلیف موارد وابسته مشخص شود؛ هنگام شکست، همهٔ داده‌ها
حفظ شوند. بررسی وابستگی و حذف اتمیک باشد و برای موفق‌کردن حذف، رابطه را خودکار قطع
یا رکورد وابسته را زنجیره‌ای حذف نکنید. یکپارچگی نشست، انتساب و فایل حفظ شود.
نشست‌ها و اطلاعات احراز هویت متعلق به خود کاربر، همراه حذف مجاز او پاک می‌شوند؛
مجوزهای متعلق به نقش نیز همراه حذف مجاز نقش پاک می‌شوند. انتساب نقش و مالکیت فایل،
حذف کاربر را تا تعیین تکلیف آن‌ها مسدود می‌کنند. مسیرهای تازه را نیز با همین سیاست
و تضمین تراکنش بررسی کنید.
