# Coordinated database and object recovery

[English](backup-restore.md) · [فارسی](backup-restore.fa.md)

برای سرویس واقعی مالک، زمان‌بندی، مدت نگهداری، بازهٔ قابل‌قبول ازدست‌رفتن داده
و هدف زمان بازیابی را تعیین کنید. Kernel این رویه و
[تمرین مصنوعی بازیابی جدا](backup-restore.md#isolated-recovery-drills) را دارد، اما backup خودکار
عملیاتی، دستور restore اپراتور یا زمان تضمینی فراهم نمی‌کند. تمرین را روی دادهٔ توسعه‌دهنده یا DB عملیاتی
فعال انجام ندهید.

یک نقطهٔ بازیابی هماهنگ حفظ کنید: SQLite و WAL/journal باقی‌مانده، همهٔ اشیای
local-private/local-public یا هر دو bucket MinIO و سیاست دسترسی، شناسهٔ release
و مهاجرت، driver و مسیر و مبدأها و مرجع نسخهٔ secret-store. SQLite فقط metadata
دارد و restore DB به‌تنهایی uploads را نمی‌سازد. backup شامل هش رمز، دادهٔ شخصی،
نشست و فایل خصوصی را محافظت کنید و secret را جدا از محل امن بازیابی کنید.

۱. شناسهٔ انتشار، سطح مهاجرت، driver و مسیر واقعی را ثبت کنید. همهٔ نویسنده‌ها،
حتی نوشتن مستقیم storage، را متوقف و جلوی restart خودکار API را بگیرید.
۲. بعد از توقف تمیز تأییدشده، DB بسته و فایل‌های journal/WAL وابسته را یکجا کپی
کنید؛ فایل اصلی را هنگام فعال‌بودن نویسنده به‌تنهایی کپی نکنید.
۳. درخت کامل فایل محلی یا هر دو bucket MinIO با key، content type و سیاست خصوصی/
عمومی را ثبت کنید؛ تغییر driver metadata قدیمی را تبدیل نمی‌کند.
۴. backup بیرون دادهٔ زنده و release باشد. زمان، اندازه، checksum، تعداد رکورد و
فهرست فقط‌خواندنی ارجاع اشیا را در manifest محافظت‌شده ثبت کنید. تکمیل کپی را
پیش از شروع دوبارهٔ سرویس و بررسی health تأیید کنید.
۵. با release متناظر و تنظیمات محافظت‌شده، DB و storage را در مسیر تازه و جدا
restore کنید. seed توسعه غیرفعال و اصل backup محفوظ بماند.
۶. پیش از API روی کپی SQLite، `PRAGMA integrity_check` با نتیجهٔ ok و
`PRAGMA foreign_key_check` بدون ردیف اجرا کنید. تاریخچهٔ مهاجرت را بسنجید؛ چون
شروع API مهاجرت را اعمال می‌کند، ارتقا را روی کپی دیگری تمرین کنید.
۷. API جدا را اجرا و health، ورود مجاز، نقش، تنظیمات، تقویم، شمارش و همهٔ ارجاع‌های
فایل را بررسی کنید. خصوصی‌ها عمومی نشوند و لوگو و content type درست باشد. زمان
دادهٔ بازیابی‌شده، مدت بازیابی و اختلاف‌ها را پیش از تأیید ثبت کنید.

restore، نشست و OTP قدیمی را هم برمی‌گرداند؛ به‌خصوص پس از حادثهٔ احراز هویت،
دربارهٔ ابطال آن‌ها پیش از بازگشایی تصمیم بگیرید. برای بازگشت واقعی دوباره نویسنده
را متوقف، دادهٔ خروجی را حفظ و DB/فایل هماهنگ تأییدشده را فعال کنید و همهٔ بررسی‌ها
را تکرار کنید. نقاط بازیابی را ادغام نکنید و مهاجرت را برای downgrade ویرایش نکنید.
[عملیات انتشار](release-operations.fa.md) فعال‌سازی و rollback را توضیح می‌دهد.
