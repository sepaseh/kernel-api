# مجموعهٔ Bruno برای Kernel API

[English](README.md)

مجموعه شامل درخواست‌های API مورد استفادهٔ برنامه‌های Kernel و نمونه‌های
ذخیره‌شدهٔ پاسخ است. درخواست‌های منتشرشده مسیرهای احراز هویت، حساب، کاربران،
نقش‌ها، تقویم، فایل‌ها، زبان‌ها و تنظیمات را پوشش می‌دهند.

## باز کردن مجموعه

1. Bruno را نصب و اجرا کنید.
2. گزینهٔ **Open Collection** را انتخاب کنید.
3. همین پوشهٔ `collection` را انتخاب کنید.
4. یک محیط محلی موجود، مانند **development**، را انتخاب یا محیط جدیدی بسازید.
   مقدار `base_url` را نشانی API محلی، مقدار `access_token` را ابتدا خالی و
   مقدار `origin` را یکی از مبدأهای دقیق مجاز سرور در `SERVER_ALLOWED_ORIGINS`
   یا `SERVER_ALLOWED_ORIGIN` قرار دهید. مبدأ مجاز ممکن است با `base_url`
   متفاوت باشد؛ طرح نشانی و در صورت تنظیم، پورت را هم وارد کنید. مجموعه آن را
   در سرآیند `Origin` می‌فرستد تا درخواست‌های دارای کوکی نشست از بررسی مبدأ
   سرور عبور کنند. برای منابع جداگانه `user_id`، `role_id` و `file_id` را با
   شناسه‌های ساختگی ایجادشده در سرور محلی موقت تنظیم کنید. پیش از ارسال
   درخواست بارگذاری، یک فایل ساختگی محلی در Bruno انتخاب کنید.
   برای حذف تاریخ تقویم، `calendar_date` را در محیط فعال برابر تاریخ موردنظر
   با قالب `YYYY-MM-DD` قرار دهید.

محیط محلی و اطلاعات ورود واقعی را در مخزن ثبت نکنید. بررسی snapshot دقیق
انتشار پوشه‌های محیط محلی Bruno را نمی‌پذیرد؛ بررسی کامل را در checkout تمیز و
بدون محیط Bruno اجرا کنید.

## درخواست‌های موجود

- احراز هویت: ثبت‌نام، ورود، درخواست OTP، نوسازی توکن، فراموشی و تغییر رمز و خروج.
- حساب: حساب جاری، ویرایش مشخصات و نام کاربری و تأیید ایمیل.
- تقویم: فهرست، ساخت و حذف تاریخ‌های تنظیم‌شده.
- نقش‌ها: فهرست، ساخت، جزئیات، ویرایش و حذف.
- دسترسی‌ها: فهرست دسترسی‌های مرتبط با نقش‌ها.
- تنظیمات سامانه: جزئیات عمومی و ویرایش با احراز هویت.
- زبان‌ها: فهرست زبان‌های پشتیبانی‌شده با احراز هویت.
- فایل‌ها: بارگذاری multipart برای نشان برنامه.
- کاربران: فهرست، ساخت، جزئیات، ویرایش، حذف، وضعیت، مدیر سامانه، رمز، نقش‌ها و تأیید موبایل.

کلاینت می‌تواند توکن داخل حافظه را از طریق `/auth/refresh-token` بازیابی کند؛
این درخواست حتی زمانی که کلاینت مشترک API آن را بدون صفحهٔ اختصاصی انجام می‌دهد
در مجموعه وجود دارد. آداپتور احراز هویت از کوکی نشست نیز استفاده می‌کند.

## نخستین اجرا

درخواست ورود را با حساب آزمایشی محلی اجرا کنید. اسکریپت پس از پاسخ، توکن دسترسی
را با نام `access_token` در محیط فعال ذخیره می‌کند. سایر درخواست‌های دارای احراز
هویت از آن توکن استفاده می‌کنند.

فایل‌های پاسخ در کنار هر درخواست و با نام کد وضعیت HTTP قرار دارند. پیام‌های
نمونه‌های خطا انگلیسی‌اند؛ نمونه‌های موفق تنظیمات سامانه‌ای با زبان فعال فارسی
را نشان می‌دهند. پاسخ موفق بدون بدنه نمونهٔ JSON ندارد.

عملیات احراز هویت و تغییر شماره ممکن است پاسخ `429` بدهند. نمونه‌های
`429.json` یکی از خطاهای ممکن را نشان می‌دهند؛ فاصلهٔ صدور مجدد کد و
محدودکنندهٔ تلاش درون‌فرایندی می‌توانند پیام‌های متفاوتی برگردانند. حوزه‌ها
و `Retry-After` در [محدودیت‌های HTTP](../docs/http-transport.fa.md) آمده‌اند.

برای تغییر شمارهٔ خود ابتدا با `POST /account/request-mobile-verification`
کد شمارهٔ جدید را درخواست کنید، سپس همان `mobile` و مقدار `otp` را به
`PATCH /account/update-profile` بفرستید. برای تغییر شماره از مسیر مدیریت،
از `POST /users/{{user_id}}/request-mobile-verification` و سپس
`PATCH /users/{{user_id}}` با همان `mobile` و `otp` استفاده کنید. مسیر مدیریت
به مجوز `users.update` نیاز دارد؛ تغییر شمارهٔ کاربر دیگر فقط برای مدیر سیستم
مجاز است. صدور و تأیید کد باید برای همان کاربر و مسیر و در همان نشست باشد.
اجرای محلی از کد توسعهٔ تنظیم‌شده استفاده می‌کند و ارسال OTP تولیدی پیاده‌سازی
نشده است. از حساب و دادهٔ ساختگی با سرور محلی موقت استفاده کنید. راهنماهای
[انتقال HTTP](../docs/http-transport.fa.md) و
[آداپتورهای احراز هویت](../docs/auth-adapters.fa.md) را ببینید.

پاسخ‌های برنامهٔ HTTP پس از مقداردهی، از جمله خطاها، پیش‌درخواست‌ها و محتوای
فایل، سرآیند `X-Request-Id` دارند. پاسخ اولیهٔ 503 پیش از آماده‌شدن برنامه این
سرآیند را ندارد. کلاینت می‌تواند مقداری با ۱ تا ۱۲۸ حرف یا رقم ASCII،
خط زیر، خط تیره یا علامت مساوی بفرستد. مقدار نامعتبر یا غایب با UUID جایگزین
می‌شود؛ مقادیری که شامل دادهٔ حساس تشخیص داده شوند، مانند شمارهٔ موبایل یا
`token=...`، نیز جایگزین می‌شوند. شناسهٔ پاسخ و گزارش یکسان است و فقط برای
هم‌بستگی به کار می‌رود، نه اثبات هویت. CORS این سرآیند درخواست را مجاز می‌کند
و در پاسخ در دسترس قرار می‌دهد؛ بدنهٔ JSON تغییر نمی‌کند.

خطاهای غیرمنتظرهٔ فراهم‌کنندهٔ احراز هویت، پایگاه داده و ذخیره‌سازی، خطای `500`
با پیام عمومی ترجمه‌شده برمی‌گردانند، نه stack یا جزئیات SDK. خطاهای موردانتظار
اعتبار و اعتبارسنجی، پاسخ‌های مستند `400` را حفظ می‌کنند؛ خطای غیرمنتظرهٔ
زیرساختی در ورود، ثبت‌نام، تغییر رمز یا ساخت کاربر به خطای اعتبارسنجی تبدیل
نمی‌شود. رمز یا توکن واقعی را در این مجموعهٔ مشترک ذخیره نکنید.

## اتصال به backend محلی

backend مستقل این قراردادها را در `src` پیاده می‌کند. `npm run dev` را با
تنظیمات صریح و مقادیر ساختگی اجرا کنید؛ این فرمان فایل محیط را خودکار بارگذاری
نمی‌کند. برای اجرای محلی به
[راهنمای توسعه](../docs/development.fa.md) و برای بررسی‌ها به
[فهرست اعتبارسنجی](../.agents/validation.json) رجوع کنید. پاسخ‌های ذخیره‌شده
خروجی اجرا را تعیین نمی‌کنند؛ هنگام تغییر رفتار، مجموعه و مسیر Hono مربوط را
هم‌زمان به‌روز کنید.

[راهنمای اتصال مجموعه و backend](../.agents/rules/api-collection.md) قواعد منبع
مرجع، ترتیب تغییرات و مالکیت را توضیح می‌دهد.

## قرارداد HTTP مشترک

درخواست‌های اجرایی در همین مجموعه‌اند. DTOها و ثابت‌های هر قابلیت در
`src/contracts/` قرار دارند.

- بدنه‌های JSON به `Content-Type: application/json` نیاز دارند و محدودیت آن‌ها
  ۶۴ کیلوبایت است، از جمله برای جریان‌های بدون Content-Length؛ نوع نامعتبر 415
  و JSON بیش از حد 413 برمی‌گرداند. محدودیت بارگذاری فایل جداگانه است.
- درخواست تغییردهندهٔ مرورگر به مبدأ دقیق مجاز نیاز دارد. مبدأ نامعتبر یا
  درخواست دارای کوکی بدون مبدأ 403 می‌گیرد. کلاینت غیرمرورگری بدون کوکی یا
  دادهٔ fetch محیطی می‌تواند از درخواست bearer استفاده کند.
- `settings.language_code` ذخیره‌شده یکی از ده زبان `ar`، `de`، `en`، `es`،
  `fa`، `fr`، `it`، `pt`، `ru` و `tr` را برای پاسخ انتخاب می‌کند. سرآیند زبان
  درخواست از جمله `Accept-Language` و کوکی بازدیدکننده آن را تغییر نمی‌دهند؛
  پاسخ‌هایی که از مرحلهٔ تعیین زبان عبور می‌کنند، زبان حاصل را در `Content-Language` اعلام می‌کنند.
- در پردازش مسیرهای احراز هویت و حساب، پس از بررسی CORS و مبدأ، `Cache-Control: private, no-store` تنظیم می‌شود؛ پاسخ‌های preflight یا خطاهای زودتر ممکن است آن را نداشته باشند.
- محدودکنندهٔ تک‌فرایندی ورود را به ۲۰ تلاش برای هر هویت در ۱۵ دقیقه محدود
  می‌کند. ثبت‌نام، صدور OTP، بازیابی، تأیید کد ایمیل و صدور و تأیید OTP تغییر
  شماره برای هر حوزه و هویت (یا کاربر اقدام‌کننده و حساب مقصد) ۱۰ تلاش در
  ۱۵ دقیقه دارند و فاصلهٔ صدور مجدد OTP نیز ۱۲۰ ثانیه است. محدودکنندهٔ
  درون‌فرایند پاسخ 429 با `Retry-After` می‌دهد؛ محدودیت مستقل صدور مجدد OTP
  می‌تواند 429 بدون این سرآیند برگرداند. این محدودکننده توزیع‌شده یا مبتنی بر IP نیست؛
  استقرار مشترک به سیاست مقابله با سوءاستفاده در ingress یا ذخیرهٔ مشترک نیاز دارد.
- تغییر یا بازنشانی رمز نشست‌های قبلی را باطل می‌کند. خروج idempotent است و
  کوکی‌های واقعی Better Auth، از جمله نام‌های secure در HTTPS، را منقضی می‌کند.

پس از آماده‌شدن برنامه، خطاهای پردازش‌شده توسط تبدیل‌کنندهٔ خطای API شامل
`{ "message": "translated message" }` و سرآیند `X-Request-Id` هستند؛ پاسخ
اولیهٔ آمادگی `503` بدون بدنه و بدون این سرآیند است. خطاهای مشترک HTTP به‌جای تکرار در نمونه‌های اختصاصی هر عملیات
اینجا مستند می‌شوند.
